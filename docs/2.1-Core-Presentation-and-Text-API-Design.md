# Icod.DCurses 2.1 Core Presentation and Text API Design

**Status:** accepted T2101 design authority for T2102-T2108  
**Compatibility baseline:** Icod.DCurses 2.0.0  
**Runtime boundary:** Icod.Terminal 1.18.0  
**Target frameworks:** `net8.0`, `net9.0`, `net10.0`

This document freezes the public API and behavior to be implemented by T2102-T2108. It is the design authority for those tranches. Later work may correct an impossibility or defect only through an explicit design amendment that identifies the affected tests and compatibility cost.

## 1. Design boundary

The accepted surface supplies immutable text layout, source/visual geometry, bounded retained presentation, constant-time viewport geometry, prepared-cell bulk writes, stateless track layout, and bounded refresh diagnostics. Text and geometry objects are usable without a terminal session. Application content and policy remain caller-owned.

The following are outside 2.1:

- document storage, edit commands, undo/redo, search, clipboard, file I/O, and editor policy;
- game worlds, entities, combat, pathfinding, procedural generation, and game-loop policy;
- callback-owned virtual content, background loading, cache eviction, and hidden full-content caching;
- a retained widget or layout tree;
- a unified public ordinary/metadata/raster retained-cell value;
- an unbounded diagnostic event log;
- any direct `Icod.TermInfo`, `TerminalDescription`, `StringCapability`, or raw escape sequence path.

No output object retains a `CursesSession`, an Icod.Terminal object, a retained screen, or a mutable caller collection. Strings may be retained because .NET strings are immutable. Other caller collections are copied eagerly.

## 2. Naming decision

The accepted rich range name is `CursesTextSpan`.

The 2.0 public API contains no type with that name. `System.Span<T>` and `System.ReadOnlySpan<T>` are stack-only memory views, while `System.Range` expresses index endpoints; neither represents styled source text. Other .NET-family libraries use text-span vocabulary, but the `Curses` prefix makes this immutable presentation range unambiguous at a call site. The type is deliberately non-generic and never exposes caller memory.

## 3. Source and rich-text foundation (T2102)

### 3.1 Exact public declarations

```csharp
namespace Icod.DCurses;

public readonly record struct CursesTextPosition {
	public CursesTextPosition( int offset );
	public int Offset { get; }
}

public sealed record CursesTextSpan {
	public CursesTextSpan(
		CursesTextPosition start,
		int length,
		CursesStyle style,
		CursesCellMetadata? metadata = null
	);

	public CursesTextPosition Start { get; }
	public int Length { get; }
	public CursesTextPosition End { get; }
	public CursesStyle Style { get; }
	public CursesCellMetadata? Metadata { get; }
}
```

`CursesTextPosition` rejects a negative offset with `ArgumentOutOfRangeException`. Its record-struct equality is offset equality.

`CursesTextSpan` rejects a non-positive length with `ArgumentOutOfRangeException`. It computes `End` with checked arithmetic and reports overflow as `ArgumentOutOfRangeException` for `length`. Record equality compares all five public values using their normal equality. The metadata reference is safe to retain because `CursesCellMetadata` is immutable.

A layout validates spans eagerly in the supplied order. Each start and end must be a legal source text-element boundary, spans must be ascending and non-overlapping, and every end must be at most the source length. An invalid element produces `ArgumentException` for `spans`, with the element index in the message. The caller's list is copied before layout proceeds. Uncovered source uses the option defaults; spans do not inherit from adjacent spans and later spans never override earlier ones.

### 4.2 Validation and capacities

`Create` throws `ArgumentNullException` for null `text` or `options`. Option values and the copied spans are validated before result arrays are published.

| Limit | Accepted range | Failure |
|---|---:|---|
| source length | 0 through 16,777,216 UTF-16 code units | `ArgumentOutOfRangeException` for `text` |
| span count | 0 through 1,048,576 | `ArgumentOutOfRangeException` for `spans` |
| columns | 1 through 1,048,576 | `ArgumentOutOfRangeException` for `Columns` |
| maximum rows | null or 0 through 1,048,576 | `ArgumentOutOfRangeException` for `MaximumRows` |
| starting column | 0 through 1,048,576, with `StartingColumn + Columns` representable as `int` | `ArgumentOutOfRangeException` for `StartingColumn` |
| tab interval | 1 through 1,048,576 | `ArgumentOutOfRangeException` for `TabInterval` |
| produced fragments | at most 4,194,304 | `InvalidOperationException` before exceeding the limit |
| produced cells | at most 16,777,216 | `InvalidOperationException` before exceeding the limit |

Undefined enum values cause `ArgumentOutOfRangeException` naming the option. A null width provider causes `ArgumentNullException` for `WidthProvider`. All additions and products that form offsets, columns, counts, or array lengths are checked before allocation.

### 4.3 Segmentation and line rules

- Source positions are UTF-16 offsets. Legal positions are zero, source length, and boundaries between the text elements accepted by the configured width provider.
- DCurses performs no Unicode normalization. Each malformed surrogate code unit is treated as U+FFFD for segmentation and width while retaining the original one-code-unit source range.
- CRLF is one hard break. Lone CR and lone LF are hard breaks. Break code units do not appear in fragments.
- Empty text produces one empty visual line. A trailing hard break produces a final empty visual line unless `MaximumRows` prevents it.
- Tabs advance to the next positive stop anchored at absolute layout column zero: `TabInterval - (absoluteColumn % TabInterval)`. The absolute column includes `StartingColumn` and line alignment.
- C0 and C1 controls other than tab, CR, and LF cause `ArgumentException` for `text` before a result is published.
- A leading zero-width element is represented in source mappings but produces no fragment or cell. A zero-width element following visible content is appended to that preceding element's fragment and maps to its trailing edge.
- A width-two element is never split. If it cannot fit on an otherwise empty line, it is clipped from that line and the layout advances past it.

### 4.4 Wrap, alignment, and overflow

| Wrap | Behavior | First enforcement |
|---|---|---|
| `NoWrap` | each logical line produces one visual line; content beyond the available width is hidden | T2103 `CursesTextLayoutTests` |
| `TextElement` | wrap at the last complete text element that fits; always advance at least one source element | T2103 `CursesTextLayoutUnicodeTests` |
| `Word` | prefer the latest whitespace boundary that fits, exclude neither source whitespace nor its mapping, and fall back to text-element wrap | T2103 `CursesTextLayoutTests` |

Alignment is applied independently to each produced visual line after wrapping. `Start` uses `StartingColumn`; `Center` adds half the unused columns; `End` adds all unused columns. Odd remainders stay after the content for `Center`.

`Clip` emits only complete visible elements. `Ellipsis` replaces the final complete visible elements as needed with U+2026 using the style and metadata of the first hidden source element, or the option defaults when the row limit hides a new line. The ellipsis fragment has an empty source range at the first hidden position and `IsEllipsis == true`. If U+2026 does not fit completely, no ellipsis cell is emitted. Ellipsis is used only on a line that hides source because of width or `MaximumRows`; it does not decorate an exactly fitting line.

`MaximumRows == 0` produces no lines, zero cells, and `IsTruncated == (text.Length != 0)`. Otherwise `IsTruncated` reports any hidden source caused by width, row limit, or an element too wide for a line.

Layout is O(inspected text elements + produced fragments + produced cells). It may allocate O(spans + lines + fragments + cells), bounded by the limits above. It never inspects content outside the supplied string and has no dependency on application document size.

Constructors reject negative lines/columns/preferred values, invalid enum values, and invalid `CursesTextPosition` inputs with `ArgumentOutOfRangeException`. ### 5.2 Mapping rules

| Case | Normative mapping | First enforcement |
|---|---|---|
| ordinary element | leading edge maps to element start; trailing edge maps to element end | T2104 `CursesTextGeometryTests` |
| soft-wrap boundary | `Leading` selects the next line at its start; `Trailing` selects the preceding line at its end | T2104 `CursesTextGeometryTests` |
| hard break | positions within CRLF are illegal; the position before the break maps to the preceding line and the position after it maps to the next line | T2104 `CursesTextGeometryUnicodeTests` |
| width-two leader | hit maps to source start with `Leading` | T2104 `CursesTextGeometryUnicodeTests` |
| width-two continuation | hit maps to source end with `Trailing`; no caret is placed in the continuation column | T2104 `CursesTextGeometryUnicodeTests` |
| attached zero-width source | maps to the trailing edge of its visible host; previous/next movement still observes its legal source boundaries | T2104 `CursesTextGeometryUnicodeTests` |
| leading zero-width source | maps to line start and is never hit directly | T2104 `CursesTextGeometryUnicodeTests` |
| clipped/ellipsis cell | maps to the first hidden legal source position; ellipsis hits report `isInside == true` | T2104 `CursesTextGeometryTests` |
| outside a line | hit clamps to its nearest edge and reports `isInside == false` | T2104 `CursesTextGeometryTests` |

`MoveVertically` preserves `preferredColumn` rather than replacing it with a short line's clamped column. `GetLineStart` and `GetLineEnd` return the legal boundaries represented by the visual line; the end excludes a hard break. Selection is half-open after ordering anchor and active. Empty selection returns an empty array. Returned rectangles use visual-line indices as rows, never include hidden source, and are clipped to `[firstLine, firstLine + lineCount)` before allocation. Mapping uses indexes built during layout and is O(log lines + local fragments); previous/next position is O(1); selection geometry is O(intersected lines + returned rectangles).

## 6. Retained presentation and prepared-cell bulk mutation (T2105)

### 6.1 Exact public declarations

```csharp
namespace Icod.DCurses;

public partial class CursesWindow {
	public void PresentTextLayout(
		CursesTextLayout layout,
		int firstVisualLine,
		int visualLineCount,
		int destinationRow,
		int destinationColumn
	);

	public void WriteCells(
		int row,
		int column,
		ReadOnlySpan<CursesCell> cells
	);

	public void WriteCells(
		int row,
		int column,
		int rows,
		int columns,
		ReadOnlySpan<CursesCell> cells,
		int sourceStride
	);
}
```

`PresentTextLayout` requires a non-null layout. Source line range arguments must be nonnegative and entirely within `layout.Lines`; zero count is allowed. Destination coordinates are window-relative and may lie outside the window so long as their arithmetic does not overflow. Presentation clips at the destination window, preserves the logical cursor, and replaces every visible cell in the requested layout-width rows, including blanks. It uses ordinary retained cells and each fragment's metadata. Replaced metadata and raster placeholders are removed under existing ownership rules. It does not refresh or touch the physical cursor.

Visual columns are absolute layout columns. During presentation, `layout.Options.StartingColumn` maps to `destinationColumn`; a fragment at visual column `c` maps to `destinationColumn + c - layout.Options.StartingColumn`. The first requested visual line maps to `destinationRow`.

`WriteCells` is accepted because Task 2 measured 1,920 scalar calls for a full 80x24 frame and material repeated-frame work. The row overload is the rectangular overload with one row, `columns == cells.Length`, and `sourceStride == cells.Length`.

Bulk destinations must be entirely inside the window; bulk writes do not clip. Dimensions and coordinates are nonnegative, and `sourceStride >= columns`. Empty rows or columns are a no-op after argument validation. The required source length is checked as `(rows - 1) * sourceStride + columns`; overflow or insufficient input causes `ArgumentException` for `cells`. Source padding is ignored.

Each source row must contain self-contained coherent cell footprints: every width-two leader is followed by a matching continuation cell, no row begins with a continuation, and no footprint crosses a row edge. Invalid input causes `ArgumentException` for `cells`. Validation, bounds checks, arithmetic, and raster ownership checks complete before any retained mutation, so failure is atomic. A caller may source cells from memory that aliases an implementation-owned array only through a public copy; the span is never retained and behaves as though copied before mutation.

Ordinary cells replace content and style and clear addressed metadata/raster state. If an addressed boundary intersects an existing width-two footprint outside the rectangle, the outside counterpart is repaired to the window background before the rectangle is applied. Only retained values that actually change are damaged; an identical bulk write produces no new damage. The logical cursor is preserved. Complexity is O(addressed cells), with zero heap allocation after validation for the row overload and at most O(columns) temporary storage for a demonstrably aliased rectangular source.

No bulk style-only operation and no unified metadata/raster value is accepted for 2.1: Task 2 did not demonstrate a distinct application-shaped benefit sufficient to justify either public contract.

```csharp
	public CursesViewport EnsureVisible( CursesCellPosition position );
	public CursesViewport EnsureVisible( CursesRectangle rectangle );
	public CursesRectangle GetVisibleContent(
		int overscanRows = 0,
		int overscanColumns = 0
	);
	public bool TryContentToViewport(
		CursesCellPosition content,
		out CursesCellPosition viewport
	);
	public bool TryViewportToContent(
		CursesCellPosition viewport,
		out CursesCellPosition content
	);

```

All extents, coordinates, and overscan values are nonnegative; constructors throw `ArgumentOutOfRangeException` otherwise. Origins are clamped, not rejected. The maximum origin in an axis is `max(0, contentExtent - viewportExtent)`. Empty content has origin zero and an empty visible rectangle. A viewport larger than content also has origin zero. Visible size is the lesser of viewport and remaining content.

`MoveTo` clamps requested coordinates. `PanBy` and `PageBy` compute with `long` then clamp, including `int.MinValue` and `int.MaxValue`. A page is the viewport extent; a zero-size viewport page has zero movement. Start means `(0,0)` and end means both maximum origins.

`EnsureVisible(position)` requires a position inside the content. It changes each origin by the smallest amount that exposes the point; an axis with zero viewport extent cannot expose the point and retains its clamped origin. `EnsureVisible(rectangle)` requires the full rectangle inside the content. For a rectangle larger than the viewport, its leading edge wins; otherwise the smallest movement wins.

Overscan expands the visible content rectangle on both sides, clips it to content, and never changes viewport state. Translation succeeds only for a coordinate inside the current visible rectangle. On failure, the out value is `default`. Every method is O(1), allocation-free, and independent of content extent.

### 7.2 Viewport edge rules

| Case | Result | First enforcement |
|---|---|---|
| empty content | origins zero; empty visibility; all translations false | T2106 `CursesViewportTests` |
| oversized viewport | origin zero; visible extent equals content | T2106 `CursesViewportTests` |
| shrinking content | origins clamp to new maximum | T2106 `CursesViewportTests` |
| extreme deltas/pages | long intermediate then clamp; never wrap | T2106 `CursesViewportBoundaryTests` |
| zero viewport extent | empty visibility; `EnsureVisible` cannot expose that axis | T2106 `CursesViewportBoundaryTests` |
| overscan at an edge | clipped to content, with no negative coordinate | T2106 `CursesViewportTests` |

## 8. Stateless track layout (T2107)

### 8.1 Exact public declarations

```csharp
namespace Icod.DCurses;

public enum CursesTrackKind {
	Fixed,
	Weighted
}

public enum CursesTrackDistribution {
	Start,
	Center,
	End,
	SpaceBetween,
	SpaceAround,
	SpaceEvenly
}

public readonly record struct CursesTrack {
	public static CursesTrack Fixed(
		int size,
		int minimum = 0,
		int? maximum = null
	);

	public static CursesTrack Weighted(
		int weight = 1,
		int minimum = 0,
		int? maximum = null
	);

	public CursesTrackKind Kind { get; }
	public int Value { get; }
	public int Minimum { get; }
	public int? Maximum { get; }
}

public static partial class CursesLayout {
	public static CursesRectangle[] ArrangeRows(
		CursesRectangle bounds,
		ReadOnlySpan<CursesTrack> tracks,
		int gap = 0,
		CursesTrackDistribution distribution = CursesTrackDistribution.Start
	);

	public static CursesRectangle[] ArrangeColumns(
		CursesRectangle bounds,
		ReadOnlySpan<CursesTrack> tracks,
		int gap = 0,
		CursesTrackDistribution distribution = CursesTrackDistribution.Start
	);
}
```

`Fixed` requires nonnegative size; `Weighted` requires positive weight. Minimum is nonnegative. Maximum, when supplied, is at least minimum. A fixed track's ideal size is `clamp(size, minimum, maximum)`; a weighted track's ideal begins at minimum. Track equality is value equality.

At most 4,096 tracks are accepted. Gap must be nonnegative. Invalid tracks, enum values, track count, checked gap total, or a sum of minima plus mandatory gaps that exceeds available space causes an exception before the result array is allocated. The parameter named by the invalid value receives `ArgumentOutOfRangeException`; infeasible minima receive `ArgumentException` for `tracks`.

All minima are reserved first. Fixed tracks then receive cells toward their clamped ideals in track order; if the ideals do not all fit, later fixed tracks remain nearer their minima. Remaining cells go to weighted tracks in proportion to weight, never beyond maximum. Integer remainder is assigned one cell at a time in ascending track index among eligible tracks. If no weighted track can accept all remaining cells, the surplus is distributed outside tracks:

- `Start`: after the last track;
- `Center`: half before and the odd remainder after;
- `End`: before the first track;
- `SpaceBetween`: among inter-track spaces, low-index spaces first; for fewer than two tracks it behaves as `Start`;
- `SpaceAround`: two half-space units per track, with outside slots one unit and between slots two; units are assigned in visual order;
- `SpaceEvenly`: among the `trackCount + 1` spaces, low-index spaces first.

The explicit `gap` is added to every inter-track space before surplus distribution. Zero tracks return an empty array. Arrangement is O(track count + distributed capped remainder), with the capped-remainder pass bounded by track count per saturation round; storage is O(track count). Row and column variants use identical arithmetic and differ only by axis.

Diagnostics are disabled by default. When disabled, `LatestRefreshDiagnostics` is always null and collection adds no attributable heap allocation after warmup. When enabled, one immutable snapshot is atomically published after each refresh attempt; the property retains only the latest snapshot. A sequence starts at one and increments with checked `long` arithmetic. Sequence exhaustion causes `InvalidOperationException` before a new refresh attempt begins.

Counters describe DCurses logical and prepared semantic work. They do not expose Icod.Terminal objects, serialized bytes, private plans, capability identities, or terminal-brand decisions. Diagnostic counters saturate at `int.MaxValue`, and the sequence saturates at `long.MaxValue`, so observation cannot make a refresh fail or change its outcome.

| Refresh result | Snapshot rule | First enforcement |
|---|---|---|
| success | `Succeeded`; logical state published; invalidation reflects final physical certainty | T2108 `CursesRefreshDiagnosticsTests` |
| cancellation before output | `Cancelled`; no logical publication; physical state remains valid | T2108 `CursesRefreshDiagnosticsTests` |
| cancellation after output may have begun | `Cancelled`; no logical publication; physical state invalidated | T2108 `CursesRefreshDiagnosticsTests` |
| output failure before any write | `Failed`; no logical publication; physical state follows the existing 2.0 certainty rule | T2108 `CursesRefreshDiagnosticsTests` |
| output failure after a write | `Failed`; no logical publication; physical state invalidated | T2108 `CursesRefreshDiagnosticsTests` |
| forced repaint after invalidation | full repaint true; outcome still reflects that attempt | T2108 `CursesRefreshDiagnosticsInvalidationTests` |

Counters contain work completed before cancellation/failure. `OperationKinds` is the union of categories actually prepared for the attempt, not claimed terminal support. Snapshot publication must not change refresh selection, cancellation, output, invalidation, retry, or logical-publication decisions. Enabled diagnostics allocate at most one snapshot per attempted refresh and retain no historical collection.

## 10. Shared coordinate, arithmetic, ownership, and damage rules

| Domain/conversion | Rule | First enforcement |
|---|---|---|
| source position | UTF-16 offset at a validated text-element boundary | T2102 `CursesTextSourceContractTests` |
| source span | half-open `[Start, End)`, sorted, non-overlapping | T2102 `CursesTextSourceContractTests` |
| visual text | zero-based visual line and absolute layout column | T2104 `CursesTextGeometryTests` |
| retained destination | zero-based window-relative row/column | T2105 `CursesTextPresentationTests` |
| viewport content | zero-based nonnegative content row/column | T2106 `CursesViewportTests` |
| viewport local | zero-based coordinate inside current visible content | T2106 `CursesViewportTests` |
| layout rectangles | existing nonnegative `CursesRectangle` cell domain | T2107 `CursesTrackLayoutTests` |

All public validation happens before observable mutation or publication. Invalid negative values and enum values use `ArgumentOutOfRangeException`; null references use `ArgumentNullException`; invalid cross-argument relationships use `ArgumentException`; a valid input whose bounded result would exceed an accepted production capacity uses `InvalidOperationException`. Arithmetic is performed in checked `int` or widened `long` intermediates and converted only after bounds are established.

| Mutation case | Rule | First enforcement |
|---|---|---|

## 11. Implementation sequence and compatibility

The public increments are implemented in this order:

1. T2102: development identity, source positions, and rich spans;
2. T2103: immutable rich layout;
3. T2104: source/visual mapping, caret movement, hit testing, and selections;
4. T2105: retained presentation and the two evidence-backed bulk writes;
5. T2106: immutable large-content viewport geometry;
6. T2107: stateless track arrangement;
7. T2108: bounded refresh diagnostics and performance qualification.

Every increment is additive to the 2.0 fingerprint. `AssemblyVersion` remains `2.0.0.0`. Production continues to reference only Icod.Terminal 1.18.0. The accepted APIs require no new Terminal feature: text segmentation, layout, mapping, viewport, bulk retained mutation, track arithmetic, damage counters, and semantic refresh counters are all DCurses responsibilities. Live terminal I/O and capability selection continue exclusively through Icod.Terminal.
