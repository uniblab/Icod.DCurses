## Purpose

T1601 freezes the representation and public-contract decisions that T1602-T1611 implement. It deliberately changes no production source and does not change package identity.

Version 1.6 remains **retained mixed-media presentation**, not a generic graphics scene graph. Terminal-backed Unicode raster placeholder cells become another retained presentation axis beside ordinary visual/text cells and terminal-independent semantic metadata, while `Icod.Terminal` remains the only live raster protocol and ownership authority.

The approved architecture authority is:

`docs/superpowers/specs/2026-09-15-icod-dcurses-1.6-retained-mixed-media-presentation-design.md`

The implementation plan is:

`docs/superpowers/plans/2026-09-15-icod-dcurses-1.6-retained-mixed-media-presentation.md`

This document freezes the exact T1601 spelling and boundary decisions deferred by those planning documents.

## Representation freeze

The retained logical representation is three-axis:

```text
Curses retained surface
    +-- dense CursesCell[] visual/text plane
    +-- optional row-sparse CursesCellMetadata plane
    +-- optional row-sparse retained-raster plane
```

The raster plane reuses the existing `CursesSparseCellPlane<T>` storage strategy with a small internal reference wrapper. No raster field is added to `CursesCell`.

`CursesCellMetadata` remains terminal-independent semantic meaning and does not carry Terminal raster ownership.

The established 64-bit large-pad reference remains:

```text
2048 x 256 = 524,288 coordinates
```

An unconditional eight-byte reference field would therefore impose 4 MiB on that pad even when no raster content exists. The sparse-plane direction is frozen unless later measured evidence proves it invalid and a new design review explicitly replaces it.

The transient internal logical state used by editing/composition becomes conceptually:

```text
CursesLogicalCellState
    CursesCell Cell
    CursesCellMetadata? Metadata
    retained-raster reference? Raster
```

Existing editing/composition algorithms must move this state together rather than creating a second raster-specific editing engine.

## Ownership layers

The supported ownership shape is:

```text
CursesSession
    -> CursesRasterResource
        -> CursesRasterPlaceholder
            -> CursesRasterCell values
```

`CursesRasterResource` and `CursesRasterPlaceholder` are ownership roots and are asynchronously disposable.

`CursesRasterCell` is an immutable presentation token. It is not independently disposable and does not own cleanup.

Internally:

- `CursesRasterResource` wraps one `TerminalRasterResource` from one canonical `TerminalSession`;
- `CursesRasterPlaceholder` wraps one `TerminalRasterPlaceholder` owned by one wrapped resource/session;
- `CursesRasterCell` retains the opaque `TerminalRasterPlaceholderCell` plus enough private DCurses ownership association to reject use through the wrong live `CursesSession`;
- no public protocol/private numeric id is introduced.

## Public lifecycle vocabulary

DCurses does **not** expose Terminal's raster lifecycle types directly. It projects the stable semantic vocabulary into DCurses types.

```csharp
public enum CursesRasterOwnershipStatus {
	Current = 0,
	Stale = 1,
	Released = 2,
	Disposed = 3
}

public enum CursesRasterOwnershipLossReason {
	None = 0,
	SessionStateLost = 1,
	ResourceMissing = 2,
	ParentPlacementLost = 3,
	AncestorReleased = 4,
	ResourceReleased = 5,
	ExplicitDisposal = 6
}

public readonly record struct CursesRasterOwnershipState(
	CursesRasterOwnershipStatus Status,
	CursesRasterOwnershipLossReason LossReason
);
```

The mapping from `TerminalRasterOwnershipState` is exhaustive by **semantic member name**, not by numeric cast. An unknown future Terminal enum value fails closed rather than silently acquiring a DCurses meaning.

Although `ParentPlacementLost` and `AncestorReleased` are not ordinary virtual-placeholder outcomes, retaining the complete reviewed Terminal 1.14 semantic vocabulary avoids later weakening or repurposing the published DCurses return type if future retained-raster facades legitimately observe those states.

Reading `OwnershipState` remains synchronous, bounded, side-effect free, and does not perform terminal I/O or verification.

## Public dependency boundary

The published 1.5 public surface already intentionally exposes:

```text
Icod.Terminal.TerminalControlResult<T>
Icod.Terminal.TerminalEndpoint
Icod.Terminal.TerminalSession
Icod.TermInfo.TerminalDescription
Icod.TermInfo.TerminalSize
```

Version 1.6 permits exactly one additional lower-layer public type:

```text
Icod.Terminal.TerminalRasterImage
```

This is intentional. Reusing Terminal's backend-neutral raster-image container avoids creating a second DCurses pixel-format/alpha/dimension/image-validation hierarchy.

Version 1.6 does **not** permit these Terminal types to leak into public DCurses signatures:

```text
TerminalRasterResource
TerminalRasterPlaceholder
TerminalRasterPlaceholderCell
TerminalRasterOwnershipState
TerminalRasterOwnershipStatus
TerminalRasterOwnershipLossReason
TerminalRasterPlacement
TerminalRasterPlaceholderOptions
```

Nor does it expose raw Kitty/Sixel ids, protocol dictionaries, generation ids, APC/DCS payloads, or backend selectors.

## Session creation API

`CursesSession` adds exactly this candidate operation:

```csharp
public ValueTask<TerminalControlResult<CursesRasterResource>> CreateRasterResourceAsync(
	TerminalRasterImage image,
	CancellationToken cancellationToken = default
);
```

Semantics:

- `image` is non-null and remains caller-owned;
- DCurses delegates the live resource transaction to its canonical Terminal session;
- a usable `CursesRasterResource` is published only when Terminal publishes a usable resource;
- DCurses retains no hidden source-image copy for replay;
- controlled Terminal unavailable/unsupported outcomes remain controlled result outcomes;
- cancellation/commit semantics remain Terminal-authoritative.

## Resource facade

Candidate surface:

```csharp
public sealed class CursesRasterResource : IAsyncDisposable {
	public CursesRasterOwnershipState OwnershipState { get; }

	public ValueTask<TerminalControlResult<CursesRasterPlaceholder>> CreatePlaceholderAsync(
		int columns,
		int rows,
		CancellationToken cancellationToken = default
	);

	public ValueTask DisposeAsync();
}
```

No public constructor exists.

`CreatePlaceholderAsync` uses Terminal's published placeholder contract and therefore accepts:

```text
columns 1..256
rows    1..256
```

Locally invalid dimensions are rejected before Terminal output.

The facade exposes no physical placement API in 1.6. Ordinary/relative physical raster scene ownership remains outside this release.

## Placeholder facade

Candidate surface:

```csharp
public sealed class CursesRasterPlaceholder : IAsyncDisposable {
	public int Columns { get; }
	public int Rows { get; }
	public CursesRasterOwnershipState OwnershipState { get; }

	public CursesRasterCell GetCell(
		int row,
		int column
	);

	public ValueTask DisposeAsync();
}
```

No public constructor exists.

`GetCell` is synchronous, bounded, side-effect free, and delegates coordinate validation/token creation to the owned Terminal placeholder. It performs no output.

## Raster-cell token

Candidate shape:

```csharp
public readonly struct CursesRasterCell {
	public int Row { get; }
	public int Column { get; }
}
```

There is no public constructor.

Public row/column values are descriptive coordinates within the placeholder and do not constitute complete token identity. Two cells with equal row/column values from different placeholders are not interchangeable.

The default value is not a valid live raster token and is rejected by write/set/refresh paths that require usable ownership.

## Logical surface API

`CursesVirtualScreen` adds:

```csharp
public CursesRasterCell? GetRasterCell(
	int row,
	int column
);

public void SetRasterCell(
	int row,
	int column,
	CursesRasterCell? rasterCell
);
```

`CursesWindow` adds the same local-coordinate operations plus:

```csharp
public void WriteRasterCell(
	CursesRasterCell rasterCell
);
```

`WriteRasterCell` writes one retained raster placeholder cell at the current logical cursor and advances by exactly one terminal column using the established wrap/scroll policy.

The ordinary visual/text `CursesCell` at that coordinate remains a separate axis. A raster cell may coexist with a blank or styled ordinary cell and with semantic metadata.

Writing/replacing ordinary text/cells clears retained raster state on the replaced logical coordinate because that write owns the visible coordinate. It does not silently clear unrelated semantic metadata except where the existing text-footprint contract already does so.

Direct `SetRasterCell(..., null)` removes only raster state; it does not mutate visual text/style or semantic metadata.

## Session association and copying

Every live `CursesRasterCell` is associated privately with exactly one owning `CursesSession` through its placeholder/resource chain.

Standalone logical surfaces may retain a token as application intent because they do not themselves perform terminal I/O.

Before a session-backed refresh emits a token, the token must belong to that exact session and have usable current ownership. Foreign-session tokens fail before output.

Operations that transfer retained state into a live session-owned destination must reject a known foreign-session raster reference before partial destination mutation.

Same-session logical copy/scroll/pad/panel operations may duplicate references to the same raster token; this does not duplicate Terminal ownership.

No API reparents a Terminal raster ownership object or manufactures a new live token from public row/column values.

## Panel transparency freeze

For `CursesPanelTransparency.BlankCellsTransparent`, a panel coordinate is transparent only when:

```text
ordinary cell is blank
AND retained raster cell is absent
```

A raster-bearing coordinate is visually present even when its ordinary cell is blank.

Semantic metadata alone does not make a blank coordinate opaque.

This rule applies consistently to full composition and incremental coordinate resolution.

## Refresh boundary

The existing `CursesRefreshEngine` remains the only physical presentation coordinator.

A composed coordinate has three retained axes:

```text
visual/text cell
semantic metadata
raster placeholder cell
```

Physical knowledge must compare all three axes.

Raster emission:

1. positions the cursor through existing refresh serialization;
2. validates session association and current ownership;
3. delegates the opaque Terminal placeholder cell to `TerminalSession.WriteRasterPlaceholderCellAsync` through a typed internal output adapter;
4. records physical raster knowledge only after successful output;
5. conservatively invalidates cached rendition assumptions needed for subsequent ordinary styled output.

DCurses never constructs the Unicode placeholder code point, combining marks, SGR identity colors, image ids, placement ids, or APC commands.

While any logical or retained physical raster state exists, line-shift, character-shift, and erase optimizations remain disabled unless a later explicitly reviewed tranche proves them raster-safe. Correctness wins over an unproven optimization.

Synchronized output remains the existing session-level refresh wrapper; no graphics-specific output gate is added.

## Lifecycle freeze

The default lifecycle strategy is lazy validation, not an unbounded reverse index from each resource/placeholder to every logical coordinate.

When Terminal ownership becomes `Stale`, `Released`, or `Disposed`:

- logical raster references may remain as retained application intent;
- refresh emits no stale/private identity;
- trusted physical raster knowledge is invalidated;
- no hidden source replay/re-upload occurs;
- no automatic backend switch occurs;
- stale/released/disposed ownership never becomes current again.

Session invalidation/suspend-resume invalidates physical raster knowledge together with existing physical-screen knowledge.

Explicit resource/placeholder disposal remains idempotent according to Terminal ownership semantics.

## Explicit T1601 exclusions

T1601/1.6 does not add:

- physical raster scene graphs or general placement ownership;
- Sixel placeholder emulation;
- backend selection/ranking inside production DCurses;
- image file decoding/transcoding;
- hidden source-image caches;
- replay/re-upload after lifecycle loss;
- raw Kitty/Sixel/APC/DCS command APIs;
- raster animation/frame scheduling;
- pixel-within-cell layout;
- widget/control hierarchy;
- callbacks or retained event capture/bubble tree;
- automatic focus-on-click;
- drag/drop payload semantics;
- timed multi-click policy;
- retained flex/grid/constraint layout;
- accessibility-tree ownership;
- terminal emulation or PTY/process hosting.
