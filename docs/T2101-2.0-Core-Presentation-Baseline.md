# T2101 Icod.DCurses 2.0 Core Presentation Baseline

**Date:** 2026-09-23.\
**Published baseline:** `Icod.DCurses 2.0.0`.\
**Assembly version:** `2.0.0.0`.\
**Target frameworks:** `net8.0`; `net9.0`; `net10.0`.\
**Direct production dependency:** `Icod.Terminal 1.18.0`.\
**Production boundary:** no direct production `Icod.TermInfo` dependency.

## Purpose

This document freezes the starting point for the 2.1 core-presentation and text
work. T2102-T2108 may add public facilities, but they must preserve the published
2.0 surface and ordinary 2.0 behavior unless a separately reviewed defect requires
otherwise.

`docs/Public-API-Fingerprint-2.0.json` is the immutable machine-readable authority
for the public contract. It is never rewritten for 2.1. Later 2.1 fingerprints are
additive artifacts with their own release identity.

## Existing presentation and text facilities

The 2.0 public surface already provides the following mechanisms:

| Facility | Published behavior |
| --- | --- |
| `ICursesTextWidthProvider` | Returns a width of zero, one or two terminal columns for one Unicode text element. |
| `UnicodeCursesTextWidthProvider` | Implements Unicode 17.0.0 width policy with explicit narrow or wide ambiguous-width behavior. |
| `CursesText` | Measures, truncates and slices printable text by terminal columns without splitting a text element. |
| `CursesWindow.Write` | Writes terminal-independent Unicode text using the screen width provider and retained style. |
| `CursesWindow.WriteWithMetadata` | Writes styled retained text with semantic cell metadata. |
| `CursesWindow.WriteCell` | Writes one prepared logical cell at the current cursor. |
| `CursesWindow.FillRectangle` | Fills a validated window-local rectangle with one ordinary cell. |
| `CursesWindow.CopyRectangleTo` | Copies a retained rectangle between windows with overlap-safe semantics. |
| `CursesWindow.OverlayRectangleTo` | Overlays nonblank retained content between windows. |
| `CursesPad` | Owns a retained off-screen surface whose storage is proportional to its full dimensions. |
| `CursesPadViewport` | Presents and pans a bounded rectangle over a pad. |
| `CursesLayout` | Provides stateless split, proportional split, dock and clip calculations. |

The retained screen records terminal-cell rows and columns. `CursesText` accepts
.NET strings but returns strings or column counts; it does not expose stable source
positions, visual lines or bidirectional mappings. `CursesPadViewport` maps pad
coordinates to a destination window but still requires storage for the whole pad.
The existing layout helpers return rectangles and retain no layout tree.

## Gaps accepted for 2.1 work

The 2.0 surface deliberately does not provide:

- immutable rich presentation spans over caller-owned source text;
- validated UTF-16 source positions or source-to-visual mappings;
- wrapping, alignment, ellipsis, caret affinity or selection rectangles;
- content/viewport geometry independent of a retained full-content pad;
- span or rectangular input for prepared retained cells;
- fixed/weighted/minimum/maximum track distribution;
- a bounded public refresh-diagnostics snapshot.

These are capability gaps, not permission to move a document model, editor command
engine, game world, widget tree, virtual-content callback, cache policy or terminal
protocol handling into DCurses.

## T2101 measurement policy

T2101 adds editor and roguelike workload characterization without changing this
production behavior. Measurements use repeated same-thread allocation samples after
warmup and take the minimum observed result. Portable allocation ceilings include a
64 KiB measurement allowance rather than treating a 256-byte difference as a
failure. Wall-clock results are informational and are not CI pass/fail gates.

The measured workloads must distinguish visible-content cost from total application
content. They must also record repeated public-call counts before proposing bulk
mutation. No public API is justified solely by looking more convenient or by reducing
the number of source lines in a sample.

## Application workload measurements

The measurements below were captured by the deliberately failing zero-ceiling runs
on commits `581cdd5` and `8abbc34` in PR workflows
[`35899460448`](https://github.com/uniblab/Icod.DCurses/actions/runs/35899460448)
and [`35900094426`](https://github.com/uniblab/Icod.DCurses/actions/runs/35900094426).
Each runtime job executes:

```text
dotnet test Icod.DCurses.sln -c <Staging|Release> --no-build --no-restore --logger trx
```

The table records the minimum of eight same-thread samples after 32 warmup
operations. Ranges cover the observed `net8.0`, `net9.0` and `net10.0` results on
Windows, Linux and macOS, x64 and ARM64. Elapsed time is not a CI gate and was not
recorded as a portable baseline.

| Workload | Deterministic shape | Observed minimum allocation | Accepted portable ceiling | 2.1 decision informed |
| --- | --- | ---: | ---: | --- |
| Editor visible slice | 10,000 caller-owned lines; inspect and write 40 lines into 80x40; 256 frames | 96,133,120-96,384,704 bytes | 93 MiB (97,517,568 bytes) | Rich layout should inspect each visible source slice once, retain useful mappings and avoid repeated helper strings. |
| Roguelike full frame | Algorithmic 2,048x2,048 world; 1,920 scalar `Move`/`WriteCell` pairs per frame; 256 frames | 11,796,480-11,797,720 bytes | 12 MiB (12,582,912 bytes) | A row/block API remains a candidate, but must separate DCurses call overhead from application-created cell-content strings. |
| Roguelike sparse update | Nine prepared one-column cells per update; 256 updates | 0 bytes | 0 bytes | The scalar retained-cell path is already allocation-free for prepared sparse content; lower call count alone does not justify a public bulk API. |
| Moved pad viewport | 2,048x256 retained pad; alternate two 80x24 source rectangles; 256 presentations | 55,252,992 bytes | 54 MiB (56,623,104 bytes) | Large documents/maps need geometry-only virtualization rather than storage proportional to all 524,288 pad cells. |
| Text helper batch | 10,000 calls each to measure, truncate and slice a fixed Unicode corpus | 78,400,000-78,880,016 bytes | 76 MiB (79,691,776 bytes) | Rich layout must avoid independently rescanning and rebuilding the same source for measurement, clipping and mapping. |
| Layout helper batch | 100,000 dock-plus-proportional-split chains (200,000 helper calls) | 0 bytes | 64 KiB measurement allowance | Existing stateless geometry is an appropriate model for new track and viewport calculations. |

The editor frame contains 969 visible cells. Repeating the identical frame through
`CursesWindow.Write` marks the same 969 cells dirty: the safe scalar write path clears
each existing footprint to the background before restoring it. This is published 2.0
behavior and a measured cost, not a T2101 defect fix. Later layout presentation or
bulk mutation may avoid that transient retained change only if it preserves wide-cell,
metadata, raster and damage semantics.

## Frozen 2.1 performance rules

- Text layout and mapping work is linear in inspected source plus produced
  fragments/cells; caret movement must not rescan a complete document.
- Viewport clamp, translation and `EnsureVisible` calculations are constant-time and
  independent of total content extent.
- Virtualized presentation memory is proportional to visible rows plus explicit
  overscan, never the complete document or map extent.
- Bulk mutation becomes public only after an application-shaped comparison shows a
  material benefit over prepared scalar writes. The nine-cell result proves that
  allocation reduction is not itself sufficient.
- Track layout remains stateless and allocation-free within the 64 KiB portable
  measurement allowance.
- Disabled refresh diagnostics add no attributable allocation after warmup. Enabled
  diagnostic state is bounded and never becomes an event log.
- Wall-clock observations remain informational until a cross-platform CI threshold
  can be justified without encoding runner noise.
