# T1001 — 1.0.0 Release-Closure Foundation

**Release line:** `1.0.0`  
**Merged contract baseline:** `0.9.0`  
**Published package baseline:** `0.8.0` until the 0.9 tag/publication gate completes  
**Post-merge baseline SHA:** `2acf166aed9c56c330025ca923c1d7cae712f913`  
**Dependencies:** `Icod.Terminal 1.4.0`; `Icod.TermInfo 1.10.0`  
**Target frameworks:** `net8.0`; `net9.0`; `net10.0`  
**Status:** release-closure foundation active

## Purpose

`Icod.DCurses 1.0.0` is release closure over the contract frozen by `0.9.0`. It is not a new feature tranche and it is not a deferred breaking-cleanup tranche.

The exact merged `0.9.0` commit passed the repository's complete `Release` main workflow across Windows x64/ARM64, Linux x64/ARM64, macOS x64/ARM64, and package/fresh-consumer validation. That green post-merge baseline is the foundation for the 1.0 release-candidate branch.

## Frozen compatibility contract

The 1.0 candidate must retain the accepted 0.9 compiled public API fingerprint:

```text
sha256:            274b87ec28a253e4891f7f72dea847eaf7d57f45e7b6dd2ae4b464e783046639
exported types:    43
contract lines:   309
```

The intentional lower-layer public type set remains exactly:

```text
Icod.Terminal.TerminalSession
Icod.Terminal.TerminalEndpoint
Icod.Terminal.TerminalControlResult<T>
Icod.TermInfo.TerminalDescription
Icod.TermInfo.TerminalSize
```

No public signature, enum numeric value, nullability contract, geometry/cell semantic, ownership rule, cancellation/disposal rule, or dependency-boundary change is accepted merely because the package major version becomes 1.0.

## Closure sequence

```text
T1001  post-0.9 merge baseline + 1.0 RC foundation
  -> T1002  1.0 public API/fingerprint carry-forward and compatibility lock
  -> T1003  final documentation/package/release-workflow audit
  -> T1004  exact 1.0.0-rc.1 six-architecture + package gate
  -> T1005  stable 1.0.0 source promotion and merge gate
```

### T1001

- verify the merged 0.9 `main` commit under `Release`;
- establish the dedicated 1.0 branch/PR;
- promote package and assembly identity to the first 1.0 release candidate;
- retain the dependency baseline;
- prohibit feature-family work.

### T1002

- carry the 0.9 machine fingerprint forward as the proposed 1.0 baseline;
- retain the 0.9 semantic/lifetime/dependency freeze tests;
- prove no public or semantic delta was introduced by the major-version promotion;
- retain historical 0.9 baselines unchanged.

### T1003

- audit README, package release notes, conceptual/migration docs, XML documentation, 1.0 roadmap, release workflow, package metadata, sample/package-consumer guidance, authors/copyright/license wording, dependency versions, and `ncurses` presentation;
- distinguish published-package state from validated-source state;
- do not rewrite historical milestone records to current versions.

### T1004

- require one exact `1.0.0-rc.1` head to pass Windows x64/ARM64, Linux x64/ARM64, macOS x64/ARM64, and package/fresh-consumer validation under PR `Staging` policy;
- retain the accepted fingerprint and complete representative acceptance suites;
- permit no feature/API expansion.

### T1005

- promote the unchanged accepted RC contract to `Version 1.0.0` / `PackageVersion 1.0.0`;
- retain `AssemblyVersion 1.0.0.0`;
- freeze the final 1.0 API/documentation/package records;
- require the exact stable-source PR head to pass the complete gate;
- leave merge, post-merge `Release` validation, `v1.0.0` tagging, NuGet/GitHub Packages publication, checksums, symbols, and GitHub Release creation as explicit later actions.

## Non-goals

T1001–T1005 do not add native `ncurses` ABI compatibility, exhaustive C curses source compatibility, forms/menus/panels, a widget toolkit, terminal emulation, PTY ownership, SSH transport, graphics protocols, complex-script shaping, transparent multi-writer locking, or a public diagnostics/performance API.

## Gate

T1001 is satisfied when the merged 0.9 baseline is proven green under `Release`, the 1.0 branch/PR exists, the first 1.0 RC package identity is established, and the frozen compatibility contract remains unchanged.
