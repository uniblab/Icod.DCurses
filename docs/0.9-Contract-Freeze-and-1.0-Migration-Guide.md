# Icod.DCurses 0.9 Contract Freeze and 1.0 Migration Guide

`Icod.DCurses 0.9.0` is the compatibility-freeze line immediately before the stable `1.0.0` closure. It is based on the published `0.8.0` package and is intentionally not another major feature release.

## What 0.9 means for consumers

The 0.9 development goal is to make accidental API or semantic changes mechanically visible before 1.0.

The initial accepted surface contains 43 exported types and 309 canonical declared contract lines. The repository stores the accepted fingerprint in `docs/Public-API-Fingerprint-0.9.json`; CI regenerates the fingerprint from each compiled target framework and fails when it changes without an explicit baseline update.

The fingerprint includes public type/member signatures, enum values, generic constraints, parameter/ref/default information, accessor visibility, and compiled nullable metadata. Separate tests pin compatibility-sensitive geometry, Unicode/cell, lifetime, cancellation, and failure semantics which cannot be inferred from reflection alone.

## Migration from 0.8

At the initial 0.9 freeze there is **no planned public API migration from 0.8**. Existing 0.8 applications should continue to compile unchanged.

If T905 identifies a pre-1.0 surface which genuinely should not survive into 1.x, that cleanup must happen during 0.9 and this document will record the exact source/behavior migration. Breaking cleanup will not be deferred to the `1.0.0` release-closure tranche.

## Session ownership

The ordinary application model remains:

```csharp
await using CursesSession session = await CursesSession.OpenAsync();
CursesWindow screen = session.StandardScreen;
```

`CursesSession` owns the presentation state and the underlying Terminal session it opens. Disposal restores curses-owned presentation and Terminal-owned host state.

Advanced callers may supply an already-open `Icod.Terminal.TerminalSession` through the existing `CursesSession.OpenAsync(TerminalSession, ...)` overload. Ownership transfers only after successful curses initialization; successful session disposal then disposes the supplied Terminal session. If curses initialization fails before transfer, the caller retains ownership.

## Concurrency model

The 0.8 hardening contract is the intended 1.x contract:

- logical `CursesScreen`, `CursesWindow`, `CursesPad`, and `CursesPadViewport` mutation is single-writer unless a member explicitly documents otherwise;
- one Terminal-owned event consumer may wait concurrently with refresh/output work;
- competing independent event-reader loops are unsupported;
- terminal-mutating curses activity is internally serialized;
- DCurses does not add per-cell locks, a public scheduler, or a second terminal byte reader.

## Cancellation and disposal

Caller cancellation and session disposal remain distinct:

- caller cancellation produces an `OperationCanceledException`-compatible result and preserves the caller token where DCurses creates it;
- canceling one wait does not discard Terminal's underlying decoder state or fragmented input;
- disposal prevents new terminal activity and unblocks pending DCurses event/lifecycle waits;
- disposal-induced cancellation of those waits is surfaced as `ObjectDisposedException`;
- repeated disposal shares one restoration operation.

A clean end-of-input remains the semantic `CursesInputEventKind.EndOfInput` event.

## Geometry and cell semantics

Coordinates supplied to windows and virtual screens are zero-based row/column coordinates.

`CursesWindow` and subwindows are shared views. A subwindow origin is parent-local; writes are projected into the shared owning logical screen.

Rows/columns describe height/width. Column-oriented text slices use half-open intervals and never split a two-column text element.

The built-in Unicode provider continues to use Unicode 17.0.0 data. East Asian Ambiguous characters are narrow by default; `UnicodeCursesTextWidthProvider.WideAmbiguousInstance` is the explicit opt-in wide policy.

Wide-cell leader/continuation footprints are repaired when an owning screen/window operation overwrites or clips one side. Semantic line cells remain distinguishable from ordinary Unicode box-drawing text even when their visible content is the same.

## Presentation and refresh

The 0.6/0.7 presentation and refresh contracts remain intact:

- logical styles are terminal-independent;
- physical presentation is capability-driven through `Icod.TermInfo`;
- unsupported presentation degrades deterministically where the established contract permits it;
- retained physical state is used only while it is known;
- uncertain output invalidates retained knowledge and a later refresh returns through a safe repaint path;
- `CursesSessionOptions.UseSynchronizedOutput` remains opt-in and defaults to `false`.

## Pads and viewports

`CursesPad` remains an off-screen logical surface. `CursesPadViewport` projects a rectangular source region into an ordinary destination window and does not own terminal state.

Multiple viewports may observe one pad independently. Presentation by one viewport does not acknowledge changes for another. Destination geometry is revalidated when a viewport presents.

## Intentional lower-layer public types

Five Terminal/TermInfo type definitions remain deliberately visible in the public DCurses contract:

```text
Icod.Terminal.TerminalSession
Icod.Terminal.TerminalEndpoint
Icod.Terminal.TerminalControlResult<T>
Icod.TermInfo.TerminalDescription
Icod.TermInfo.TerminalSize
```

They provide the advanced Terminal-session integration seam, canonical endpoint identity, controlled live-size result, and immutable TermInfo escape hatch. DCurses does not duplicate those lower-layer concepts merely to hide their namespaces.

No additional Terminal/TermInfo type may leak into the public surface without an explicit fingerprint and dependency-boundary review.

## Native curses compatibility

Icod.DCurses is a managed curses-style API, not a native ABI wrapper. `ncurses` ABI compatibility, exhaustive C source compatibility, forms/menus/panels, terminal emulation, PTY management, and widget-toolkit frameworks remain outside the 1.0 core contract.

## Compatibility gate before 1.0

Before 0.9 is stable, the release gate will require:

- the accepted public API fingerprint;
- semantic freeze tests;
- nullable/XML documentation and dependency-boundary review;
- package-only consumption from the generated artifact;
- editor-like, pager-like, Unicode-heavy, rich-input, lifecycle, pad, cancellation/failure, sparse-refresh, and high-frequency acceptance;
- Windows x64/ARM64, Linux x64/ARM64, and macOS x64/ARM64 validation across `net8.0`, `net9.0`, and `net10.0`;
- exact package dependency metadata for `Icod.Terminal 1.4.0` and `Icod.TermInfo 1.10.0`.

After stable `0.9.0`, `1.0.0` is intended to be release closure over that accepted contract, not another feature or breaking-change tranche.
